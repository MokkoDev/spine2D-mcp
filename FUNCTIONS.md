# Function catalog

This is the MCP tool catalog. **Implemented** tools are callable now. **Planned** tools describe later work and are not registered with the MCP server. Planned inputs and outputs below are design targets, not current API schemas. Implemented JSON editing is currently limited to tested Spine 4.2 and 4.3 exports; other versions can be inspected, but validation flags them and edits are rejected.

For tool selection, call `spine_workflow_guide` with `goal: "choose"`. It groups common requests by source and desired result and names the primary tools for each workflow. Use `spine_capabilities` with `area`, `query`, or `status` to narrow the catalog when you need a specialized function. For one JSON edit, use the named edit tool; for several related edits in one validated stage, use `spine_preview_edit`. All JSON edit tools return an `editId`; `spine_commit_edit` saves the selected stage.

For JSON tools, `path` or `dataPath` means a Spine skeleton JSON file. For CLI tools, `projectPath` means a `.spine` project file. A later implementation will define exact schemas and safety rules before enabling planned tools. Spine's [JSON format](https://en.esotericsoftware.com/spine-json-format) includes bones, slots, skins, attachments, constraints, events, and animation timelines; its [CLI](https://en.esotericsoftware.com/spine-command-line-interface) supports import/export and batch operations.

| --- | --- | --- | --- | --- |

| `spine_run_export_profile` | Implemented | `workspaceDir`, profile `name`, `outputDir`; `inputPath` for data or media exports, `imagesDir` for atlas packing; optional `atlasName`, `timeoutMs` | New `runDir`, per-step output paths, SHA-256 hashes, `manifestPath`, profile hash and version metadata | Run the profile's data, media, and atlas settings in one new output directory. Remove that run directory if any step fails. |
| `spine_batch_job` | Implemented | `action` (`start`, `status`, `cancel`); `jobId` for status/cancel; for start, 1–20 `targets` (`path`, 1–20 `animations`), one `operation`, optional `commit` and `stopOnError` | `jobId`, job status, done/total/failed progress, per-project staged edit IDs or commit paths, and errors | Apply one retime, loop closure, or curve cleanup operation to selected animations across JSON projects. |

The profile stores JSON settings snapshots, so edits to the original settings files do not change a saved profile. Data settings require `class: "export-json"` and `nonessential: true`; an explicit data `version` must match the target runtime major/minor version. Media settings require a supported export class; atlas settings must be a JSON object. A profile's target runtime major/minor version must match its selected editor version, and a JSON `inputPath` must match that version. The profile verifies snapshot hashes when read. `spine_run_export_profile` writes a manifest containing the profile hash, input hash, atlas input image hashes, settings hashes, output file hashes, and step results. For a data export, supply a `.spine` project as `inputPath`; media export can also accept Spine data files. Saved settings still determine the actual Spine export options, and the Spine CLI checks them when run. A run with media output needs a display and OpenGL. Atlas packing needs `imagesDir` and writes outside it.

For `spine_batch_job`, `start` accepts `operation: { "kind": "retime_animation", "scale": 2 }`, `{ "kind": "make_loop", "duration": 1, "smooth": true }`, or `{ "kind": "cleanup_curves", "mode": "simplify", "tolerance": 0.01 }`. Each target names one JSON `path` and its animation names, such as `{ "path": "/path/to/rig.json", "animations": ["walk", "run"] }`. A target's animations are staged together as one atomic edit. The default `commit: false` leaves source files unchanged and returns edit IDs for review and `spine_commit_edit`; `commit: true` saves each validated project group in order. Errors are recorded per project and later targets continue unless `stopOnError: true`. Cross-project commits can therefore be partial. `status` and `cancel` use the returned `jobId`; cancellation stops before the next project and cannot undo a completed commit. Jobs live only in the connected server session. A staged edit persists for seven days, including across server restarts.

CLI tools discover `SPINE_CLI_PATH` (an executable or its installation directory) or a Spine executable on `PATH`, pass arguments without a shell, enforce a timeout, redact license holder details from command output, and return `SPINE_CLI_*` errors for execution failures. Import and export require an explicit editor version; use the version of the source project and matching runtime. Saved JSON export settings must use Spine's current `class: "export-json"` format with `nonessential: true`. Fresh project creation was verified with Spine 4.2 and 4.3. Real import/export and rendering were verified with Spine 4.3 Professional and pinned official Spineboy Essential and Pro examples, including edited bone, slot, event, draw order, curve, and deform timelines. Licensed Spine 4.2 and 4.3 Professional also imported and reexported new IK, transform, and physics constraints, imported new path constraints on pinned Vine examples, and imported and reexported new weighted meshes, linked meshes, paths, bounding boxes, clipping polygons, points, and regions. Both versions imported the project again after removing unused attachments, named skins, an animation with an event key, that event definition, and a constraint. The explicit `npm run test:cli` gate repeats these checks when a licensed CLI is available.

Stages are stored for seven days at `~/.local/state/spine2d-mcp/stages/` by default; set `SPINE_MCP_STATE_DIR` to choose another stage directory. A server restart can reload an edit ID, its diff, and its request ID. Reusing `requestId` with the same source and operations returns the same stage; using it for different contents returns `IDEMPOTENCY_CONFLICT`. Repeating a successful commit returns the original commit result. Tool errors have stable `code` and `message` fields. The source JSON is never modified during preview. A commit writes history under `.spine2d-mcp/history/<editId>/` beside the JSON file and replaces the source with a same-directory rename. Each change manifest records the source version, arguments, hashes, dependencies, time changes, and diagnostics. A commit reports success only after the manifest says `committed`. If the final manifest write fails after source replacement, the tool returns `COMMIT_FINALIZATION_FAILED` with `sourceApplied: true`; retry the same edit ID to finalize its prepared manifest.

`spine_round_trip_edit` currently requires a `.spine` project that exports exactly one skeleton JSON file. It copies saved settings into a unique run directory, checks that the data export enables Nonessential data, copies a local images directory when needed, and leaves the original project unchanged. The edit ID points to the exported baseline JSON; the staged JSON is imported into a new `edited.spine` project in the run directory. The tool re-exports that project, validates the result, and compares all staged skeleton data with the re-exported JSON. `animation.fidelity.semantic` reports a total difference count and up to 100 JSON pointer paths with staged and re-exported values; `animation.fidelity.reviewNeeded` also reflects these differences. The comparison preserves array order and checks setup data, attachments, references, key values, and curves. It allows JSON object member order and whitespace, Spine patch versions and generated skeleton hash/bounds, documented omitted defaults and empty sections, hex color letter case, and absolute numeric differences below 0.0001. It also reports selected-animation duration and key/timeline count deltas. The tool renders the original exported JSON and imported project and compares normalized frame samples. For Spine 4.2, it renders the full clip before selecting requested frame indices because an explicit saved range can export only frame zero. `motionReview` combines structural and rendered-frame hints; optional `contactRegions` add visible foot-drift review hints. The run manifest records source, settings, and output hashes plus paths and comparison metrics. On failure, the run directory remains with `failure.json` identifying the failed step. Inspect the rendered frames because pixel difference and foot-region drift are heuristics. Spine's [CLI guide](https://en.esotericsoftware.com/spine-command-line-interface) describes import, export, and the display requirement for media; its [import guide](https://en.esotericsoftware.com/spine-import) explains why Nonessential data should be exported for reimport.

The full staged change list is available through the `spine-edit://<editId>/changes` MCP resource returned as `diffResourceUri`. Tool results return at most 100 changes, summarize large key values, and report `changesTruncated` and `changeValuesTruncated`. They also include structured content alongside their JSON text content.

Bulk key selectors use exact timeline names as returned by `spine_inspect_animation`; omitted selectors include all timelines in each chosen animation. Time changes preserve key order and adjust absolute Bézier X controls. An edit that crosses or newly coincides with a non-event key fails with `KEY_ORDER_CONFLICT`; preexisting ties are preserved. Event keys may share a time. Deleting every key removes the timeline property, since Spine rejects an empty timeline array. The `offset` action changes an existing scalar numeric field and currently rejects timelines with Bézier curves because their value controls need type-specific updates. The original JSON is unchanged until `spine_commit_edit` succeeds.

`spine_clone_animation` rejects an existing destination name and preserves source keys, values, and unfamiliar fields. It transforms all supported bone, slot, constraint, deform, event, attachment, and draw-order timeline times together, including absolute Bézier X controls. For example, `timeScale: 2, startAt: 0.25` places a source key at 1 second at 2.25 seconds in the new clip. Use `spine_preview_edit` to clone and then stage additional edits to the new clip in one batch.

`spine_reverse_bone_animation` creates a new clip whose continuous bone transform values play backward. It reflects Bézier handles in time, reverses event times, and adds time-zero anchor keys where a source bone timeline ends before the clip duration. The operation requires every bone timeline to start at time zero so setup-pose behavior is unambiguous. It rejects stepped curves and timelines with discrete state, such as attachments or draw order, because their exact time reversal needs additional state keys. The source clip remains unchanged; use a staged preview to inspect the result before commit. The `reverse` mode of `spine_transform_animation` has the same limits.

`spine_transform_animation` accepts these mode-specific fields in both its direct tool and `spine_preview_edit` batches:

| Mode | Required fields | Optional fields | Behavior and limits |
| --- | --- | --- | --- |
| `variant` | `sourceAnimation` | Positive `timeScale`, nonnegative `startAt` | Copies every supported timeline and transforms key and Bézier times. Equivalent to `spine_clone_animation`. |
| `reverse` | `sourceAnimation` | Positive `duration` | Reverses continuous bone motion and events with the limits of `spine_reverse_bone_animation`. |
| `mirror` | `sourceAnimation` | `bonePairs` as distinct existing `[left, right]` names, `eventMap` with defined event names | Exchanges paired bone timelines, negates horizontal translation, rotation, and shear values and Bézier Y controls, and remaps chosen event names. Supports bone transform and event timelines only; setup poses and artwork must suit a visual mirror. |
| `combine` | `firstAnimation`, `secondAnimation` | Nonnegative `secondStart` | Overlays distinct timeline paths, shifts the second clip's keys and Bézier controls, and merges event keys in time order. Rejects non-event timeline conflicts. |
| `segment` | `sourceAnimation`, nonnegative `from`, `to` greater than `from` | — | Creates a clip for `[from, to]`, shifts retained keys to local time, splits bone transform Bézier curves exactly at both boundaries, carries discrete state at the start, and filters events. A continuous non-bone timeline crossing either boundary is rejected with `UNSUPPORTED_SEGMENT_BOUNDARY`; place boundary keys first. The summary reports `requestedDuration`, actual `duration`, and inserted `boundaryKeys`. Event-only clips may end before the requested time. |

For example, `{ "path": "/path/to/rig.json", "mode": "segment", "sourceAnimation": "walk", "newAnimation": "walk-step", "from": 0.2, "to": 0.8 }` stages an extracted clip. Review the diff and diagnostics, then commit its `editId`. Unsupported mode options fail with `INVALID_TRANSFORM_OPTIONS`.

`spine_generate_motion` accepts these recipe objects. Every recipe requires `duration` in seconds (0.1–60) and creates a new clip; the target names must already exist in the rig. Omitted numeric parameters use the defaults shown in parentheses.

| `recipe.type` | Required rig fields | Optional parameters | Generated timelines |
| --- | --- | --- | --- |
| `idle` | `bone` | `swayDegrees` (3), `bobDistance` (2) | A looping rotation sway and vertical bob on one bone. At least one parameter must be positive. |
| `breathing` | `bone` | `amount` (0.04) | A looping scale change on one bone, with a small opposite horizontal scale. |
| `blink` | `slot`, `openAttachment`, `closedAttachment` | `at` (45% of duration), `hold` (8% of duration) | A slot attachment sequence; both names must exist in the default skin. |
| `walk` | `leftLeg`, `rightLeg` | Paired `leftArm` and `rightArm`, `rootBone`, `strideDegrees` (25), `bobDistance` (2) | Alternating leg and optional arm rotations, plus optional vertical root bob. |
| `run` | `leftLeg`, `rightLeg` | Paired `leftArm` and `rightArm`, `rootBone`, `strideDegrees` (45), `bobDistance` (5) | Faster gait structure with larger default stride and optional root bob. |
| `recoil` | `bone` | `angleDegrees` (-25) | One quick bone rotation, a small overshoot, and return. |
| `follow_through` | `primaryBone`, `secondaryBone` | `angleDegrees` (20), `lag` (0.18 of duration) | Primary swing and delayed secondary response. |

For example, `{ "path": "/path/to/rig.json", "newAnimation": "walk-auto", "recipe": { "type": "walk", "duration": 1, "leftLeg": "leg-left", "rightLeg": "leg-right", "rootBone": "root" } }` stages a walk. Generated numeric bone keys use eased Bézier curves; loop recipes close at their first values. The result includes `structuralReview` and `reviewNext`. Gait recipes rotate local bones without solving foot contact, so render with `spine_render_staged_edit` and inspect planted-foot intervals with `spine_analyze_motion_quality`. Its visible-region drift is a review hint, so inspect the actual PNG frames. Revise parameters by staging another request, then commit the chosen `editId`. `blink` needs artwork for both attachments, and its attachment timing is discrete.

`spine_retarget_animation` reads a validated source skeleton JSON and stages a new animation in a validated target JSON. Source and target must share the same Spine major/minor version. `maps` contains optional name dictionaries: `bones`, `slots`, `skins`, `events`, and `constraints` (nested by timeline section, such as `{ "ik": { "aim": "targetAim" } }`); `attachments` is nested by **source slot**, such as `{ "hand": { "open": "grip" } }`. Omitted names map to themselves. The tool checks mapped source names and referenced target elements, returning `UNMAPPED_REFERENCES` with missing or incompatible mappings before staging anything. Draw-order timelines require the mapped source setup slot order to match the entire target setup slot order. Deform timelines require identical source and target mesh UVs, vertices, triangles, and hull; weighted meshes also require the mapped bone index order to match. Sequence timelines require matching sequence definitions, and mapped events require matching default values. The source and target hashes are checked before commit, and the manifest records the source dependency. Different setup transforms can change the visual result even when references map cleanly, so compare a rendered preview before committing. In a `spine_preview_edit` batch, the `retarget_animation` operation additionally requires `sourceHash`, available from `spine_inspect_project`.

`spine_save_bone_pose` stores up to 256 numeric bone transform timelines as values relative to each bone's setup pose; it covers rotate, translate, scale, shear, and one-axis variants. It samples the source animation at the requested time, using setup-relative defaults before the first key. It does not capture slot, deform, constraint, event, or draw-order state. The full immutable pose can be read at `spine-pose://<poseId>/data`; poses last for the server session, and the oldest is evicted when more than 20 are saved. `spine_apply_bone_pose` maps source bone names to target names using `boneMap`, requires matching Spine major/minor versions and all mapped bones to exist, and stages typed key edits. `blend: 0.5` writes values halfway between the target animation's sampled channel values and the saved pose. If a value edit touches a Bézier segment, the default `curvePolicy: "reject"` returns a curve error; `curvePolicy: "linearize"` explicitly clears affected curve controls and reports the reset. Review a render before committing when the target skeleton has different setup transforms or hierarchy.

`spine_save_pose` also records the selected slot attachments, taking the setup attachment before a slot's first animation key. With no `bones` or `slots` filter, it captures keyed numeric bone transforms and slot attachment timelines. It reports timeline types it skipped, such as colors, constraints, deform, draw order, and events. Read the full pose at `spine-full-pose://<poseId>/data`. `spine_apply_pose` can map bone and slot names to a compatible rig, with `attachmentMap` nested by source slot (for example `{ "eyes": { "closed": "shut" } }`). Mapped attachment names must exist in the target default skin. `mirrorPairs` swaps captured bone names and negates mirrored rotation, horizontal translation, and shear offsets. The `boneMap` then maps those resulting names to target bones. `offsets` is keyed by resulting bone, timeline type, and numeric field, such as `{ "right": { "rotate": { "value": 5 } } }`. Bone channels can blend with `blend` in (0, 1]; discrete slot attachment state requires `blend: 1`, or `applySlots: false` to skip slots. Poses remain in the current server session, and staged edits still need review and commit.

`spine_save_mesh_pose` samples sparse deform keys into full coordinate arrays. Before the first key, coordinates are zero; between keys, it samples linear, stepped, or normalized Bézier interpolation. Read the immutable values at `spine-mesh-pose://<poseId>/data`. `spine_apply_mesh_pose` requires matching Spine major/minor versions, direct mesh attachments with identical UVs, setup vertices, triangles, and hull, and the same mapped bone order for weighted meshes. Linked meshes are rejected. It stages a full deform key in the target clip; `blend` mixes each coordinate with the target clip's sampled value. The target clip can be new or existing. The pose store holds the latest 20 poses in this server session. Review the staged diff and render before commit. Spine's [JSON deform format](https://us.esotericsoftware.com/spine-json-format) defines sparse offsets and interpolation.

`spine_make_loop` uses the latest pose key as the default duration; you can supply a later duration. It requires a time-zero key on every pose timeline so it can match the actual animated start pose. It excludes event triggers from pose closure and flags events at or beyond the loop end for review. Automatic easing covers bone rotation, translation, scale, and shear timelines with version-aware Bézier channel counts; other transforms, colors, deform, attachments, and draw order are closed and reported for visual review. `smooth: false` only matches endpoints. Use `spine_compare_previews` and `spine_check_animation` before committing a loop.

`spine_set_curve` maps normalized Bézier controls to Spine's absolute key times and values for each bone channel. For example, `controls: [0.25, 0, 0.75, 1]` eases between the selected key and its next key. The final key has no outgoing segment. This tool currently supports only bone rotation, translation, scale, and shear timelines; other curve types remain future work.

`spine_cleanup_curves` handles numeric bone transform timelines, including one-axis variants. In `simplify` mode, omitted `tolerance` means zero; the tool removes an interior key only when a linear segment between its neighbors stays within the chosen value difference throughout the original motion. For Bézier segments, it uses a conservative control-point bound; stepped segments are retained. First and last keys, `protectedTimes`, and keys with unfamiliar fields are retained. The summary reports the largest accepted error bound. In `smooth` mode, it keeps every key time and value, preserves stepped segments, and writes monotone cubic Bézier controls with zero endpoint and protected-key tangents. Smooth mode changes motion between keys, so review a staged render before committing. Neither mode edits slot, constraint, deform, or event timelines.

Rig operations can be staged together in `spine_preview_edit`, in dependency order: `upsert_bone`, `upsert_slot`, `upsert_skin`, `upsert_attachment`, `set_mesh_geometry`, `set_mesh_weights`, `upsert_constraint`, `upsert_event`, `upsert_animation`, then animation keys. The individual `spine_upsert_*` and mesh tools stage one operation each; commit the returned `editId` to save it. Bone `values` support `x`, `y`, `rotation`, `scaleX`, `scaleY`, `shearX`, `shearY`, `length`, `inherit`, `skin`, and `color`. Slot `values` support `attachment` (a lookup key or `null` to clear), `color`, `dark`, and `blend`. Region `values` support `name` (the actual attachment name), `path` (image path), `x`, `y`, `rotation`, `scaleX`, `scaleY`, `width`, `height`, and `color`. For multiple skin variants of one slot key, the tested editor import pattern keeps the default skin empty for that key, puts each variant in a named skin, and gives each variant a distinct actual name and image path. Skin `values` optionally replace its `bones`, `ik`, `transform`, `path`, `physics`, or `constraints` name lists while retaining attachments. Event `values` support default `int`, `float`, `string`, `audio`, `volume`, and `balance`. Numeric setup fields must be finite; region dimensions must be positive. Referenced parents, bones, slots, and skins must exist by the time their operation runs. These tools preserve unrelated JSON fields and reject replacing an attachment with a different type. Put image attachments at the skeleton's `images` path, using their `path` or attachment name plus `.png`.

`spine_upsert_constraint` accepts `constraintType` (`ik`, `transform`, `path`, `physics`), a name, `edition: "professional"`, and setup references. IK, transform, and path use `bones` plus `target`; physics uses one `bone`. A path target is a slot with a path attachment. In Spine 4.2, constraints are written to their separate `ik`, `transform`, `path`, or `physics` array and new constraints receive the next order number. In Spine 4.3, they are appended to the unified `constraints` array; the tool writes `source` for a transform target and `slot` for a path target. For 4.3 transform constraints, provide `values.properties` as an array of active channels (`rotate`, `x`, `y`, `scaleX`, `scaleY`, `shearY`); the tool creates default property ranges. Other supported setup values include IK mix/softness/bend and stretch flags, transform offsets and mixes, path modes and spacing, and physics influence, limit, FPS, and force settings. Only provided fields are changed on an existing constraint. The edition declaration prevents accidental Essential workflows; Spine itself verifies license support on import. Constraint authoring and reexport were checked with licensed Spine 4.2 and 4.3 Professional. Custom 4.3 transform property ranges remain planned.

Keyframe selectors use `{ "section": "bones", "target": "arm", "timelineType": "rotate" }` for bone transforms, the same `target` pattern for slots and constraints, `{ "section": "events" }` or `{ "section": "drawOrder" }` for direct timelines, and `{ "section": "attachments", "skin": "default", "slot": "body", "attachment": "mesh", "timelineType": "deform" }` for attachment timelines. Supported bone types are rotate, translate, scale, shear, their one-axis variants, and inherit; slot types are attachment, rgba, rgb, alpha, rgba2, and rgb2; constraint types are IK, transform, path, physics, and Spine 4.3 slider; attachment types are deform and sequence. Values are checked by timeline type. For example, a bone rotate key uses `{ "value": 25 }`, a slot attachment uses `{ "name": "hand" }`, and an event uses `{ "name": "footstep" }` with optional payload fields. New color keys require their color fields. Keys at an exact time are updated; other times insert a key. Event keys at the same time are distinguished by name. Inserting inside an existing Bézier segment returns `CURVE_SPLIT_REQUIRED`; changing a key value adjacent to a Bézier segment returns `CURVE_VALUE_EDIT_REQUIRES_LINEARIZE`. Setting `curvePolicy: "linearize"` explicitly clears affected segments and reports curve resets. Deleting a key also clears an affected Bézier segment. Use `spine_set_curve` after insertion to define new easing. The full edit is validated before it can be committed.

`spine_analyze_motion_quality` includes the structural checks from `spine_check_animation`, including its large deform-offset hints. The region bounds are fractions of the frame size; frame numbers are inclusive. The tool finds the center of visible pixels in each region and reports `POSSIBLE_FOOT_SLIDE` when that center moves beyond the threshold during the selected interval. Missing visible pixels produce `CONTACT_REGION_EMPTY`. These are review hints: rotation, changing silhouettes, and other artwork inside the selected region can move its visible center without actual foot sliding. For a JSON input, Spine derives the skeleton name from the JSON filename. The preview tool selects that name automatically, including for temporary staged files; for `.spine` projects, the optional `skeleton` selection or saved settings apply. Frames are returned in numeric order.

`spine_compare_previews` returns `contactSheetUri` with one sampled pair per row, before on the left and after on the right. Each `pairs` entry also has `sideBySideUri`, `meanAbsoluteDifference` (0–1), and `changedPixelPercent` (0–100, using a channel difference threshold of 8/255). The images are centered on a shared checkerboard canvas and transparency is composited before comparison. Different export bounds or camera framing can raise the difference even when the pose is similar; keep export settings consistent and inspect the images alongside the numbers. The contact sheet and pair images live in a new `spine-comparison-*` directory under `outputDir` and use the same `spine-preview://` resource format.

Pass the `previewId` from `spine_render_preview` or `spine_render_staged_edit` to `spine_contact_sheet` for an ordinary clip contact sheet. It samples frames evenly from first to last and returns a PNG resource. The preview must still be available in the same server session.

Pass the same `previewId` to `spine_analyze_preview` for visual quality checks, or to `spine_check_animation` together with the skeleton JSON path and matching animation name to combine visual and structural hints. Rendered previews record their input path and SHA-256 hash. Combined checks require both to match the supplied JSON; a different file or a changed file returns `PREVIEW_SOURCE_MISMATCH`. For an uncommitted preview from `spine_render_staged_edit`, pass its `editId` with the original source `path`; structural checks then use that edit's staged JSON snapshot. After committing the edit, the same preview can be checked against the committed JSON without `editId`. A preview rendered for another animation returns `PREVIEW_ANIMATION_MISMATCH`. A preview rendered directly from a `.spine` project has no matching JSON file provenance for these combined tools; use `spine_analyze_preview` for its frames or render a JSON export. `spine_round_trip_edit` verifies its imported project and re-exported JSON hashes and binds `afterPreviewId` to that re-exported JSON path and hash. The same provenance rule applies to `spine_analyze_motion_quality`. Frame analysis samples at most 60 frames and reports `samplesTruncated` when it cannot inspect the full clip. It counts pixels above the alpha threshold and flags sudden changes for review; such changes can be intentional. Use `fixedCanvas: true` only when the export uses one fixed frame size; a variable-size preview returns `VARIABLE_CANVAS` for that check. Edge contact is a clipping review hint, not proof that artwork left the canvas. Foot sliding and mesh appearance still require human review.

`spine_upsert_attachment` accepts `attachmentType` as `region`, `mesh`, `linkedmesh`, `boundingbox`, `path`, `point`, or `clipping`. Use `values` for fields defined by that attachment type. A new region needs positive `width` and `height`. A new unweighted mesh needs flat `uvs` and `vertices` coordinate pairs, `triangles` as zero-based vertex-index triples, and `hull` as the number of leading hull vertices; weighted vertices use Spine's encoded bone-index format. A linked mesh needs a source mesh in the same slot; set `values.parent` to its attachment key. The server writes `parent` in Spine 4.2 and `source` in Spine 4.3. Polygon attachments need `vertexCount` and `vertices` (flat pairs or weighted encoding); paths also need curve `lengths`. Existing fields the tool does not edit are preserved. The staged validator checks slot, skin, and linked mesh references, but an editor import is still recommended before production use.

For example, after creating slot `body` and adding `images/shirt.png`, stage a four-vertex mesh with `spine_upsert_attachment` using `{ "skin": "default", "slot": "body", "name": "shirt", "attachmentType": "mesh", "values": { "path": "shirt", "uvs": [0,0,1,0,1,1,0,1], "vertices": [-16,-16,16,-16,16,16,-16,16], "triangles": [0,1,2,2,3,0], "hull": 4, "width": 32, "height": 32 } }`. Then call `spine_set_mesh_weights` with one influence list per UV vertex. Each influence names a bone and supplies local bind coordinates plus a positive weight; weights for each vertex must sum to one. The tool encodes the current skeleton's bone indices and rejects missing or repeated bones. `spine_set_mesh_geometry` replaces all four geometry arrays using unweighted x/y pairs; it rejects a vertex count change when linked meshes or deform timelines depend on the mesh, and rejects a deform capacity change while deform keys exist. These edits remain staged until `spine_commit_edit`.

`spine_remove_attachment` accepts an exact skin, slot, and attachment key. If the attachment is still used, it returns `ATTACHMENT_IN_USE` with up to 100 reference paths and the total count. Clear setup and slot keys, delete deform or sequence timelines, remove linked meshes, or update path constraints before removing their attachment. These cleanup operations can precede `remove_attachment` in one `spine_preview_edit` batch, so either the complete change stages or none of it does. A named skin can lose an attachment used by setup or slot keys when the default skin still supplies that key; removing the default attachment requires clearing those keys. The tool removes an empty slot attachment map with its last entry.

`spine_remove_skin` deletes a named skin and all its attachments. It rejects the default skin. If an animation still has an attachment timeline in that skin, a linked mesh in another skin points into it, or removing it would leave setup, slot, or path constraint references without a default-skin fallback, the tool returns `SKIN_IN_USE` with reference paths. Clear those uses in a preceding operation in the same staged batch, then remove the skin. The result is validated before it can be committed.

`spine_remove_constraint` selects a constraint by type and name and keeps the remaining order. It checks named-skin membership and constraint timelines. Spine 4.2 stores types in separate arrays with `order` ordinals; Spine 4.3 stores them in one `constraints` array. `spine_remove_event` checks event keys in every animation. Both return up to 100 exact reference paths and a total count when in use. Stage key deletion or skin-list updates before removal in the same `spine_preview_edit` batch. Neither removal requires a Professional edition declaration because it only deletes existing data.

`spine_remove_animation` can precede `remove_event` or `remove_constraint` in an atomic batch when the clip contains the last references to those definitions. Its summary reports the removed timeline and key counts. All three removals remain staged until `spine_commit_edit`.

## Backend key

`server` means no Spine integration; `json` means editing exported skeleton JSON; `cli` means invoking the Spine command line; `json+cli` means both. The `spine_capabilities` result includes this backend for each tool.
